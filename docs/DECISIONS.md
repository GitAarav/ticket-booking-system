# Decisions Log

`REQUIREMENTS.md` captures decisions locked in *before* any code was written. This file captures decisions made *during* the build — the ones that only came up once real code existed to react to. Newest at the bottom, grouped by checkpoint.

## Checkpoint 0 — Scaffold

**Local Postgres instead of Neon for development.** The target deploy database is Neon (per `SYSTEM_DESIGN.md`), but signing up for a Neon account mid-build would have blocked progress on something outside the code. The machine already had Postgres 18 and pgAdmin installed locally via Homebrew. A `ticket_booking` database was created locally instead; `server/.env` points at it. Real Neon/Upstash/SendGrid credentials are only needed at Checkpoint 12 (deploy) and Checkpoint 9 (email) — there's no reason to provision them earlier.

## Checkpoint 1 — Auth

**Sign-in-with-Google/Firebase considered and rejected in favor of bcrypt + JWT built by hand.** OAuth doesn't remove the need for a role-guard system — the app still has to issue its own session and track customer/organiser/admin, since Google has no concept of those roles. It also adds a fourth external account (on top of Neon/Upstash/SendGrid) plus OAuth consent screen and redirect-URI configuration. Plain bcrypt+JWT is a smaller total surface area and stays inside code the project already owns — it also directly demonstrates backend/API design skill, which is part of what this assignment is evaluated on.

## Checkpoint 2 — Admin venues/seats, and the follow-up audit

**Async route errors handled via one shared `asyncHandler` wrapper, not try/catch per route.** Express 4 does not forward a rejected promise inside an `async` route handler to the error middleware automatically — an unhandled rejection there just hangs the request. Wrapping every route once avoids repeating that boilerplate everywhere, and was retrofitted into Checkpoint 1's auth routes and the `/health` route too, once the gap was found during the Checkpoint 2 self-audit.

**Admin self-registration closed off.** The original `/auth/register` trusted whatever `role` the caller sent — anyone could register as `"admin"` and get full admin powers, a complete authorization bypass. Fixed by restricting public registration to `customer`/`organiser` only. Since that removes the only path to ever create an admin account, `npm run seed:admin` (`server/src/db/seedAdmin.js`) was added as the out-of-band way to create one, driven by env vars rather than an open HTTP route.

**Bulk seat creation capped at 500 seats per request, with category-ownership validation.** Without a limit, one request could insert an unbounded number of rows and tie up a database connection. Without the ownership check, a `categoryId` from a *different* venue could be attached to a seat, corrupting the data model. Both are cheap checks done in the route before the write.

**`deleteVenue` checks for dependent shows before deleting, returning a clean `409`.** `shows.venue_id` has no `ON DELETE CASCADE` (deliberately — deleting a venue should never silently delete real bookings' shows), so an unguarded delete would surface a raw Postgres foreign-key error as an opaque `500`. A pre-check with a specific error message is clearer for both a human caller and for debugging.

**`password_hash` exposure prevented with one shared `toSafeUser()` helper.** `findUserByEmail` does `SELECT *`, so it returns the hash. Originally only the login route remembered to strip it out via manual destructuring — fragile as more routes get added. Centralizing it in `authService.toSafeUser()` makes "safe" the only path, not something every future caller has to remember.

## Checkpoint 3 — Organiser events/shows

**Shows can be created against any admin's venue, not just venues "owned" by that organiser.** Nothing in `REQUIREMENTS.md` ties an organiser to a specific admin or venue — an admin manages venues as a shared physical resource, and any organiser schedules a show at any existing venue, the way a real cinema chain's booking platform works (the venue owner and the event scheduler are different roles with no 1:1 relationship). `POST /organiser/events/:id/shows` therefore only checks that the venue and every referenced category exist — it does not check who created the venue.

**Show creation is one database transaction: the show row, all `show_pricing` rows, and the full `venue_seats → show_seats` copy happen together.** If any part fails (e.g. a bad category), nothing is left half-created — this was verified by attempting a show with incomplete pricing and confirming zero `shows` rows were left behind.

## Checkpoint 6 — TTL sweep (post-catch-up cleanup)

**`sweepJob.js`'s release loop passes the shared `pool` directly to `attemptSeatTransition()` instead of manually checking out and releasing a dedicated `client` per seat.** The original version called `pool.connect()` / `client.release()` around every single release — unnecessary, since each seat's release is a single standalone statement, not part of a multi-statement transaction (unlike `holdSeats`/`createShow`, which genuinely need one dedicated connection to keep several statements atomic together). `pool.query()` already does the checkout-run-release cycle internally in one call. Found during a code-walkthrough review, verified afterward by manually forcing a seat into an expired state and confirming the sweep still released it correctly.

## Checkpoint 7 — Cancellation & waitlist

**`waitlist_entries` gained an `offered_seat_id` column, added via a new migration rather than editing `001_init.sql`.** The original design only tracked which *category* a customer is waiting for — correct while waiting, since no seat is assigned yet. But once an offer is made, the sweep's expired-offer cascade needs to know exactly which seat to re-offer to the next person in line, even after that seat's own status has already flipped back to `available` on its own. Without storing it explicitly, that information would be lost the moment the seat-level sweep ran.

**`offerNextInWaitlist()` selects the next waiting entry with `SELECT ... FOR UPDATE SKIP LOCKED`, not a plain `SELECT`.** Two bookings in the same category could get cancelled within milliseconds of each other, both trying to offer a freed seat to "the oldest waiting entry" at the same time — without this, both could read the same row before either marks it `offered`, offering two different seats to the same customer while the actual next-in-line person gets nothing. `FOR UPDATE` locks the selected row; `SKIP LOCKED` makes a concurrent caller skip past it to the next waiting entry instead of blocking — the standard Postgres pattern for safely picking the next item off a shared queue.

**Bug found and fixed during verification: `attemptSeatTransition()`'s `'available'` branch only accepted seats coming from `status = 'held'`.** That was correct for its original use case (Checkpoint 6, releasing an expired hold), but `cancelBooking()` calls the same transition on a seat that's `'booked'`, not `'held'` — a confirmed booking being cancelled. The mismatch meant the `UPDATE` silently matched zero rows: the booking got marked `cancelled` correctly, but its seat stayed stuck as `booked` forever, and `offerNextInWaitlist` found nothing to offer. Fixed by widening the guard to `WHERE status IN ('held', 'booked')`. Caught by hand-testing the actual cancel → offer flow end-to-end, not by inspection — a reminder that this project's testing philosophy (real requests, real database checks) earns its keep here.

## Checkpoint 8 — Time-limited offer confirm link

**`POST /offers/:token/confirm` deliberately has no `authenticate`/`roleGuard` middleware at all — it lives outside the customer-authenticated router entirely.** The signed token itself is the credential, the same pattern as a password-reset link: whoever holds the specific, unguessable, time-limited link is treated as authorized for that one action, no separate login required. This matches the requirement directly — a waitlisted customer clicks a link from an email and completes the booking, nothing else.

**The offer token's expiry is computed from the target `offer_expires_at` timestamp, not a fresh "now + 15 minutes" at issuance time.** `issueOfferToken(waitlistEntryId, expiresAt)` takes the exact expiry moment and works backward to `expiresIn` seconds. This matters because it means the same token can be safely *regenerated* later (e.g. at actual email-send time in Checkpoint 9, rather than only right when the offer is first created) and will still expire at the identical real-world moment as the database's own `offer_expires_at` — the two can never drift apart, because the token computation always derives from the database column, not a separate clock.

**The confirm route reuses `seatService.confirmBooking()` unmodified — no separate "offer confirm" booking logic was written.** Per `SYSTEM_DESIGN.md`'s original intent: an offer *is* a hold (the seat is already `held`, pre-assigned to this specific customer, via the exact same `attemptSeatTransition()` used everywhere else) — so completing it is mechanically identical to a normal hold→confirm, just entered through a different door (a token instead of a login session).

**Replay protection came for free, without writing any extra code for it.** After a successful confirm, the seat's status is `'booked'`, not `'held'` — so a second attempt with the same token fails inside `confirmBooking()`'s own guard (`status = 'held' AND ...`) exactly the way any other already-booked seat would. Verified by literally reusing the same token twice and confirming the second attempt gets a clean `409`.

## Checkpoint 9 — QR + email (SendGrid), fault-isolated

**The `email_outbox` row is inserted inside the *same* transaction as the thing it's about — booking confirmation and waitlist offers both — never as a separate step afterward.** `confirmBooking()` and `offerNextInWaitlist()` each insert their outbox row right alongside their other writes, before `COMMIT`. This is the guarantee `SYSTEM_DESIGN.md` names explicitly: "confirmed" and "email queued" can never disagree, because they're the same atomic write. Sending the email is a completely separate, later step (the sweep job) — deliberately decoupled from this transaction.

**QR codes are generated at send-time, not stored anywhere.** `QRCode.toDataURL(booking_reference)` is cheap and deterministic — there's no reason to persist a QR image in the database when it can be regenerated instantly from the one piece of data it actually encodes (the opaque booking reference, never raw seat/customer data, per the original design). Same reasoning applied to the offer link's token in Checkpoint 8 — nothing gets stored that can be cheaply recomputed from data that's already there.

**Failed email sends retry up to `MAX_ATTEMPTS` (5) before giving up permanently (`status = 'failed'`), rather than retrying forever.** An unconfigured or genuinely broken SendGrid key would otherwise retry every single sweep tick indefinitely, forever incrementing `attempts` with no path to resolution — capping it means a permanently-broken config becomes visible (`status = 'failed'`, `last_error` explains why) instead of silently spinning forever in the background.

**A waitlist-offer email checks the entry's *current* `status` before sending, and silently marks itself `'sent'` (skipped) if the offer is no longer `'offered'`.** The sweep only runs every ~10 seconds, so by the time an email is actually about to be sent, the offer could already be confirmed or expired through some other path. Sending a dead link at that point would be actively wrong, not just late — so the check happens right before send, using live data, not whatever was true when the outbox row was first created.

**Verified without ever configuring a real SendGrid key — this is exactly the fault-isolation test the checkpoint asks for, just naturally already true rather than requiring the key to be deliberately broken.** A real booking was confirmed with `SENDGRID_API_KEY` empty; it succeeded immediately regardless. Its outbox row was watched through all 5 retry attempts (`last_error: "SENDGRID_API_KEY not configured"` each time) until it reached `status = 'failed'` — and the booking's own `status` was checked at that point too: still `'confirmed'`, completely untouched by the email pipeline's failure the entire time. **Real end-to-end email delivery (an actual message landing in an actual inbox) still needs a real SendGrid API key, which requires signing up at sendgrid.com — that's the one piece of this checkpoint that needs the project owner, not something that can be verified without it.**

## Checkpoint 10 — Real-time seat map

**Publishing happens in the outer, transaction-owning functions (`holdSeats`, `confirmBooking`, `cancelBooking`, the sweep), right after their `COMMIT` — never inside `attemptSeatTransition()` itself.** `attemptSeatTransition` can succeed on one seat and then have that success rolled back moments later if a *later* seat in the same multi-seat request fails (the whole point of the Checkpoint 5 all-or-nothing transaction). Publishing from inside it would tell subscribers about a change that then gets undone — a real correctness bug, not a cosmetic one. Publishing only after a confirmed `COMMIT` means every notification corresponds to something that genuinely, permanently happened.

**The realtime interface (`server/src/realtime/pubsub.js`) always delivers locally through one single `EventEmitter`, even when Redis is active — Redis only ever carries messages, never delivers them to a local SSE connection directly.** The subtlety: if `publish()` both emitted locally *and* forwarded to Redis, and the app was also subscribed to that same Redis channel (needed so *other* server instances receive the message), the publishing instance would receive its own message back through Redis and could deliver it twice locally. The fix: when Redis is configured, `publish()` *only* calls `redisPub.publish(...)` — local delivery happens exclusively through the app's own `pSubscribe` callback re-emitting into the local bus, so there is exactly one delivery path regardless of whether Redis is in the picture, and a message can never double-deliver to a local subscriber.

**The SSE payload is a lightweight "something changed" ping, not the seatmap itself — the handler always re-fetches fresh via `getShowSeatmap()` on every notification.** This reuses the exact same function that serves the REST `GET seatmap` endpoint (per `SYSTEM_DESIGN.md`'s explicit intent: one `seatMapSerializer()` for both, so they can never drift apart), and avoids a subtler risk: if the *payload itself* were published and two changes landed close together, a slow subscriber could end up applying them out of order with a stale embedded snapshot. Always re-fetching on notify means each push reflects true current state, no matter how many changes happened in between.

**Redis pub/sub is implemented but not verified against a live Redis instance — only the in-process `EventEmitter` path (the one that actually runs, since `REDIS_URL` is unset in dev) has been proven correct.** The interface is written so the SSE handler and every publisher are identical either way; swapping in a real Redis URL at deploy time (Checkpoint 12) shouldn't require touching this code, but that swap itself is untested until a real Redis instance exists.

**Known gap for Phase C (frontend integration), not fixed now: browsers' native `EventSource` can't set custom headers, so it can't send `Authorization: Bearer <token>` the normal way.** This route was kept consistent with every other route (header-based auth, verified via `curl`, which can set headers) rather than weakening the whole app's auth pattern to work around a problem specific to one browser API that only matters once a concrete frontend tool is chosen. When the frontend is built, this needs either a `fetch`-based SSE polyfill (which can set headers) or a token-via-query-param fallback added to this one route specifically.

## Checkpoint 11 — API contract freeze

**`GET /admin/ping` (the Checkpoint 1 test route proving `roleGuard` worked) is deliberately excluded from `docs/API_CONTRACT.yaml`.** It was scaffolding to prove a mechanism during early development, never a real product feature, and the frontend has no reason to ever call it — freezing it into the contract would suggest otherwise. The contract documents all 29 real endpoints across `/health`, `/auth`, `/admin`, `/organiser`, `/customer`, and `/offers`.

**The contract is a single OpenAPI 3.0 YAML file, not a hand-maintained Postman collection.** OpenAPI is plain text (diffable, reviewable in a PR, no separate export/import workflow to keep in sync with the code), tool-agnostic, and Postman imports it directly — satisfying both the "OpenAPI" and "Postman" halves of this checkpoint's own name with one artifact instead of two that could drift apart from each other.

**Verified two ways, not just written by hand and trusted:** the file was checked against a real OpenAPI 3.0 validator (`@apidevtools/swagger-cli validate`), not just parsed as YAML — confirming it's spec-compliant, not merely syntactically valid text. Then one representative example payload (`POST /auth/register`) was sent to the real running server exactly as documented, and the real response was diffed against the documented response schema — confirming the contract describes what the server actually does, not what it was intended to do.
